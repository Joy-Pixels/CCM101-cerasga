# 💭 Mission 6 - Reflection

Before this mission, I thought deploying a full application meant typing a long list of commands and hoping I didn't forget anything. It wasn't until I wrote my first `docker-compose.yml` file that I truly understood what Infrastructure as Code really meant. Turning a setup into a single reusable blueprint changed how I see a cloud engineer's job. Instead of memorizing flags for `docker run`, I described the Nextcloud and MariaDB containers once, and one command created the network and started everything together. The file can also be saved in Git so another engineer can reproduce my setup exactly, which makes collaboration so much smoother.

One thing that really stuck with me was how strict YAML is about indentation. I learned that a single Tab instead of spaces can break the entire file, and Compose will stop with a parsing error before anything even deploys. Even having too many or too few spaces can put a setting under the wrong service, which completely changes what the code means. This forced me to be careful and to check my file with `cat` before running it. At first I thought it was annoying, but now I understand that this strictness is what makes YAML reliable and predictable.

We also used environment variables like `MYSQL_PASSWORD` to pass settings into the containers without changing the images themselves. This matters because both services needed matching values so Nextcloud could log into MariaDB. It keeps configuration separate from the image, which means the same image can be reused with different settings. In a real deployment, I would not hardcode passwords in a file on GitHub; I would use secrets or an `.env` file instead. Learning this made me realize that security is not just about firewalls, it is also about how you handle sensitive information in your code.

Deploying Nextcloud in just a few minutes honestly felt like a real accomplishment. Seeing the setup page appear after one command and a short wait for the images to download made me realize how much work container images and Compose take care of. Installing a web server and a database and connecting them by hand would normally take much longer. It was strange because I kept thinking about how this same tool is probably running right now on actual servers somewhere, and I just set it up on my own in a matter of minutes. That gap between "this is just a class activity" and "this is real enterprise software" was honestly the most eye-opening part for me.

Back in Mission 1, I honestly thought cloud computing was mostly about storing files online or renting a virtual machine. I never really thought about who builds the systems behind those services. Now I realize that cloud computing is actually a lot of careful planning, where every container, network, and configuration has to be set up on purpose. It is not something that just works on its own; someone has to design it step by step and make sure it can be repeated. That shift in thinking made me appreciate how much responsibility a cloud engineer really carries.
